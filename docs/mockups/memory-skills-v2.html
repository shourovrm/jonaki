Memory and skills v2: what was remembered, what is waiting

On the test phone, after two weeks of use, Memory holds 5 facts for all threads and 1 thread fact, and Skills has no proposal. The background model (MiMo V2.6 Flash, picked as the cheapest priced model) did run: the usage sheet of a thread shows 2 turns on it that the user never chose. So extraction works and finds almost nothing, and the app never says so. Every path that ends in "nothing saved" is silent: a fact held for review, an answer with no operations, a model that failed, a proposal refused because five are waiting. These screens make each of those visible, in the thread, on the thread list, and on the Memory and Skills screens. Dark first, light beside it.

In the thread: one quiet line after extraction

After a run that extracted memory, the transcript gets one muted system line. It says what happened in five words and opens the Memory screen. The same line reports a failure, so a missing key or a broken answer is seen the first time, not after two weeks.

Thread list: what is waiting

Facts held for review and skill proposals are the two things the user must act on, and both live three taps away today. One row above the threads counts them. It is gone when nothing waits.

Memory screen: review first, then a log

Facts waiting for review go to the top with Keep and Discard, as the code already does when the section is not empty; what is new is the help line that says what memory is for, and the log at the bottom. The log lists every background call: when, which model, and what came of it. It is the only place a user can see "the model answered with nothing" without adb.

Skills: proposals you can see

A proposal is written by the model and waits for the user. Today it is listed only at the top of Skills, five block any new one, and a refused proposal is reported to the model alone. Here the proposal is announced in the thread, counted on the thread list, and dated on the Skills screen; one older than 14 days is dropped so the cap cannot stay full.

Approvals sheet: the Jev row becomes a switch

The sheet under the shield chip lists Ask, Auto and Bypass for this thread and then a row "Jev guard · On" that cannot be touched. The row becomes a switch for this thread, with the one line that says what it does. Without an OpenRouter key the switch is off and locked, and the line says why.

A thread is read after 8 new messages, or when you leave it with 2 or more. Facts from a thread that read web pages wait for review.

Safety check · A second model checks risky actions and web text. Jev, through OpenRouter. · Needs an OpenRouter key. Add one in Settings.

Code behind each screen

System line: MemoryExtractor already knows the outcome (plan applied, Failed, unreadable); it writes a hidden BACKGROUND usage row today, which becomes a visible row with a result text.
Waiting row: observePendingReview and SkillProposals.list() already exist; the thread list only needs their counts.
Memory log: the BACKGROUND rows plus a result column; the request log filter that hides them (requestSentAtMillis) is lifted for this page.
Trigger: MESSAGES_PER_EXTRACTION from 20 to 8.
Jev switch: a per-thread field next to the thread's approval mode; the global one stays in Settings.
