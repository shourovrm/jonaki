# Jonaki version 1 plan

Version 1 of Jonaki is an Android app in which a user chats with an AI agent in
separate threads. The agent searches the web, summarises YouTube videos, writes
HTML reports, remembers facts per thread and globally, uses skills, runs small
programs, uses phone features, connects to MCP servers and delegates work to
subagents. The decisions behind every part are in `DECISIONS.md`; this plan
says in which order the parts are built and how each is checked. A proposed
decision needs the user's ruling before the milestone that depends on it
starts. Every step ends with a release build, its tests and a commit.

## Module layout

Every swappable part is one Gradle module that depends only on `core/`
(D-007). A shared convention plugin in `build-logic/` keeps each module's
build file to a few lines.

```
app/                      application, navigation, ToolRegistry, dependency wiring
build-logic/              Gradle convention plugins
core/model/               Thread, Message, ToolCall, ToolResult, Memory: plain data classes
core/tool-api/            Tool interface, ToolContext, SideEffect, Capability, output truncation
core/provider-api/        ChatProvider interface, streaming events
core/agent/               agent loop, prompt builder, compaction, permission broker, subagent runner
core/storage/             Room database: threads, messages, memories, artifacts, tasks
core/files/               thread folders, import and export helpers
core/ui/                  Compose theme and shared components
feature/chat/             chat screen, step cards, approval cards
feature/threads/          thread list and thread settings
feature/memory/           memory screen
feature/settings/         keys, providers, tools, Python
feature/onboarding/       first-run tool picker
providers/openai-compatible/   OpenAI, OpenRouter, DeepSeek, GLM, MiMo, Ollama presets
providers/gemini/              native Gemini API
search/tavily/  search/ollama/  search/exa/
runtimes/quickjs/  runtimes/pyodide/
tools/read-file/  tools/write-file/  tools/edit-file/  tools/find-files/
tools/search-files/  tools/share-file/  tools/web-search/  tools/web-fetch/
tools/youtube-summarize/  tools/run-code/  tools/artifact/  tools/memory/
tools/delegate/  tools/phone/  tools/schedule/  tools/mcp/
```

The tool contract in `core/tool-api` is the centre of the design. A first
sketch, to be fixed in M2 with tests:

```kotlin
interface Tool {
    val name: String                     // "web_search"
    val promptLine: String               // one line in the system prompt
    val guidelines: List<String>         // added only while the tool is active
    val parameterSchema: JsonObject      // sent only while the tool is active
    val sideEffect: SideEffect           // READ_ONLY or CHANGES (needs approval)
    val requiredCapabilities: Set<Capability>  // for example PYTHON
    val timeLimit: Duration
    suspend fun run(arguments: JsonObject, context: ToolContext): ToolOutput
}
```

`ToolContext` gives a tool its thread folder, an HTTP client, a cancellation
signal and the truncation helper, and nothing else. A tool that needs a
backend (search, runtime) receives it through its constructor in
`ToolRegistry`, so the tool module never depends on a backend module.

## Performance budgets

These are targets to measure against, not measurements.

| Measure | Target | How it is measured |
|---|---|---|
| Cold start to usable thread list | under 1 s on a mid-range phone | Macrobenchmark startup test |
| Release APK size without Python | under 15 MB | size of `app-release.apk` |
| Tool schemas plus system prompt | under 3,500 tokens with all tools on | token count in the in-app request log (developer setting) |
| First streamed token shown | provider latency plus under 100 ms | timestamps in the in-app request log |
| Idle memory | under 150 MB | Android Studio profiler |

## M0 Spikes and project skeleton

M0 tests the five assumptions that could change the design before any
feature is built on them. Each spike is a throwaway test app or test, and
each ends with the `Outcome` of its decision filled in.

| Step | Question | Pass condition | Decision |
|---|---|---|---|
| 0.1 | Test phone | `adb devices` lists the phone | none |
| 0.2 | Skeleton | `gradle testReleaseUnitTest assembleRelease` succeeds with `app`, `build-logic`, `core/model`, `core/tool-api` and one example tool module, without new toolchain downloads | D-006, D-007, D-021 |
| S-1 | Does the bundled SQLite driver (`androidx.sqlite:sqlite-bundled`) support FTS5 with the trigram tokenizer on Android? | A test inserts mixed Bangla and English facts and finds them by a three-letter fragment | D-009 |
| S-2 | Does Pyodide run in a hidden WebView offline after download, and can files move between the thread folder and its virtual file system? | A script reads a CSV from the thread folder with pandas and writes a result file back | D-013 |
| S-3 | Does Gemini summarise a public YouTube URL from the phone within the free tier? | A 20-minute video returns a summary; time and tokens recorded | D-012 |
| S-4 | Do Tavily and Ollama web search work from the phone, and what do their quota errors look like? | Both return results; the quota error format is recorded for the fallback logic | D-011 |
| S-5 | Does Jev pick the right skill, relevant memories and the durable-fact gate for Bangla, English and mixed messages? | On 40 sample messages (half Bangla or mixed), skill and memory picks match a hand-labelled answer in at least 80 percent; latency and cost per call recorded | D-022 |

Size: medium. Nothing in M1 starts until S-1 and 0.2 pass.

## M1 Streaming chat with threads

M1 delivers a usable chat app without tools. The user adds an API key, creates
threads, and chats with streamed answers.

1. `core/provider-api` and `providers/openai-compatible` with server-sent
   events streaming; presets for DeepSeek and OpenRouter first.
2. `core/storage`: threads and messages; every streamed chunk is saved as it
   arrives.
3. API keys encrypted with Android Keystore.
4. The agent loop runs in a foreground service.
5. `feature/threads` and `feature/chat` with Markdown rendering and a Stop
   button.

Check: a test with a fake provider streams a scripted answer into the
database; on a device, a DeepSeek answer streams, and killing the app during
streaming then reopening it shows the saved part of the answer. Size: medium.

## M2 Agent loop, tool contract and file tools

M2 makes the chat an agent. The loop sends tools, runs tool calls, saves each
step and repeats until the model answers in text.

1. Tests first: loop with a scripted fake provider (tool call, result, final
   answer); step budget reached; tool time limit exceeded; user presses Stop.
2. `core/tool-api` with output truncation and spill-to-file, tested first.
3. Prompt builder: stable system prompt, one line per active tool, changing
   details (time, date) in the latest message.
4. Permission broker: read-only tools run; tools with side effects raise an
   approval card (allow once, allow for this thread, deny).
5. Tool modules: `read-file`, `write-file`, `edit-file` (multi-edit,
   exact-then-fuzzy matching, tests first), `find-files`, `search-files`.
6. Step cards in the chat show each tool call live.

Check: unit tests for each tool and the loop pass; on a device, "create a
file notes.md with three ideas, then change the second" ends with the right
file in the thread folder. Size: large.

## M3 Web search, web fetch and YouTube

1. `search/tavily`, `search/ollama`, `search/exa`; `tools/web-search` tries
   them in the user's order and moves on at a quota error; options `site`,
   `freshness`, `count`, `include_content` (each page capped at 5,000
   characters).
2. `tools/web-fetch` with jsoup and Readability4J, `max_length` default
   10,000 characters, spill-to-file above it.
3. `providers/gemini` and `tools/youtube-summarize` (URL, prompt, start, end,
   low media resolution for videos over 30 minutes).

Check: tests with recorded responses for each backend and the fallback; on a
device, "summarise the latest video from channel X" finds the video through
`web_search` limited to youtube.com and returns a summary. Size: medium.

## M4 Memory and compaction

1. Memory table and full-text index, as S-1 decided.
2. `tools/memory` (remember, forget, recall) with global and thread scope.
3. Background extraction on a cheap model: when the user leaves a thread or
   every 20 messages, returns add, update and delete operations; tests first
   with scripted model output.
4. Injection of global and thread memory up to about 1,500 tokens each,
   pinned and recently used first.
5. `feature/memory`: add, edit, delete, pin, promote to global, link to the
   source message; optional review mode for extracted memories.
6. Compaction between messages with the structured summary (Goal,
   Constraints and Preferences, Progress, Key Decisions, Next Steps, Critical
   Context); originals stay in the database.

Check: a fact stated in thread A appears in thread A's memory and not in
thread B's prompt; a promoted fact appears in both. Size: large.

## M5 Skills

1. Skill library in app storage: one folder per skill with `SKILL.md`.
2. Import from a file, a URL or a GitHub folder; edit and delete in settings;
   enable per thread.
3. Prompt listing of name, description and path; loading through
   `read_file`.
4. Built-in skills: report, slide presentation, YouTube summary, formal
   letter in Bangla.

Check: a skill imported from GitHub is listed in the prompt and the model
reads it when the task matches. Size: small.

## M7 Subagents

1. Agent type definitions (name, description, model, default tools,
   instructions), with researcher, YouTube summariser and writer built in.
2. `tools/delegate`: one task or a list run in parallel (at most 4 at once),
   no conversation context passed, capped final answer, no further
   delegation, step and cost budget.
3. `request_tool` through the permission broker; the 3-minute rule from
   D-015: after 3 minutes without an answer the subagent skips that part and
   continues, or stops and returns what it has with the skipped parts listed.
   Tests first, with a virtual clock.
4. `ask_parent`, at most two per subagent.
5. `notes` board per delegation group (post, read).
6. Collapsible subagent cards in the chat.

Check: three parallel researcher subagents compare three products and the
main agent produces one report; a test proves that an unanswered tool
request is skipped after 3 minutes and appears in the returned skipped list.
Size: large.

## M8 Code runtimes and the tool picker

1. `runtimes/quickjs` and `tools/run-code` for JavaScript.
2. `runtimes/pyodide`: download over HTTPS with checksum check, install,

3. `feature/onboarding`: tool groups with one-line descriptions and

4. Settings, Python: install, remove, packages, storage used; just-in-time

Check: with Python absent, a Python request shows the install card; after

## M9 Phone and schedule tools

1. `tools/phone`: calendar list and add, reminder, notify, clipboard read and
   write, open another app (D-020). Each permission is requested only when
   its action is first used.
2. `tools/schedule` on WorkManager: create, list, cancel; a scheduled task
   runs a prompt in its thread and posts a notification.

Check: "every morning at 8, summarise the news on X" runs once at a test time
and posts a notification with the summary. Size: medium.

## M10 MCP, Jev helper and provider presets

1. `tools/mcp`: one proxy tool with search, describe and call; remote servers
   over Streamable HTTP through the official Kotlin MCP SDK; connect on first
   use; cached tool lists.
2. `core/decider-api` and `deciders/jev` (D-022): one call per user message
   for skill pick, memory relevance and the durable-fact gate; web_search
   result filtering; hints placed in the latest message; answers under 0.6
   confidence or slower than 1.5 s ignored; fallbacks when off.
3. Settings, Jev: on/off, a switch each for skills, memory and search
   filtering, endpoint (OpenRouter or TypeSafe) and key, cost so far.
4. Presets for GLM, MiMo, Ollama Cloud, local Ollama and OpenAI.

Check: a public remote MCP server's tool is found with `mcp(search)` and
called; with Jev on, the request log shows fewer prompt tokens per message
than with Jev off on the same 20 test messages, and the skill picks match
S-5's labels. Size: medium.

## Risks

| Risk | Effect | Response |
|---|---|---|
| FTS5 or trigram unavailable in the bundled SQLite (S-1) | Weaker Bangla search in memory | FTS4 with a simple tokenizer; embeddings later |
| Pyodide too slow or memory-heavy on low-end phones (S-2) | Python tasks fail on cheap phones | Mark Python as needing 4 GB RAM; keep JavaScript as the default runtime |
| Free search tiers change | Search stops working | Several backends with fallback; user can add a key |
| Gemini changes YouTube URL support or free limits | Summaries stop working | Error message that says why; transcript route kept as a later option |
| Jev weak on Bangla messages (S-5) | Wrong skill or memory hints | Use Jev only for English messages, or only above a confidence threshold; fallbacks stay |
